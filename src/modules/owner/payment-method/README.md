# modules/owner/payment-method

Which payments the store accepts. **One payment method per type**, fixed list of five (`constants/payment-providers.ts` `METHOD_TYPES`): Tunai, Kartu Debit/Kredit, Transfer Bank, E-Wallet, QRIS. Left: the list with an on/off switch each; right: the selected method's settings.

Backed by `pos-kasir-be`:
- `/master/payment-methods` (`internal/master/payment_method`) — `name`, `type`, `status`, `image` (QRIS), and for `type=card`: `card_types` (debit/credit) and `mdr_percent` (the "MDR Default"). Card networks were dropped (they don't affect reports): the screen doesn't send them and the backend no longer has them. **POST/PUT are `multipart/form-data`**, list fields as repeated form fields; PUT replaces every field, so the section always resends the saved values (`methodPayload`). The backend clears card fields for non-card types.
- `/master/payment-channels` (`internal/master/payment_channel`) — the banks (`type=bank`, shared by card and transfer) and e-wallets (`type=ewallet`) **the store itself uses**, not the customer's bank. Each has an optional `account_number` (bank account no. / e-wallet phone no.) and `account_name` (holder) that the cashier shows to a customer who wants to transfer; the cashier role can read them (`GET`). Choosing a channel at payment is optional. Same multipart shape; PUT replaces every field, so any PUT must resend `mdr_percent`, `account_number` and `account_name` (`channelPayload` in the section does).

Behaviour:
- **On/off switches save immediately** (list row or "Aktifkan metode ini"). Turning on a type the store has no row for creates it. Inactive methods/channels are rejected at payment by the backend (`PAYMENT_METHOD_INACTIVE` / `PAYMENT_CHANNEL_INACTIVE`).
- **Card / QRIS settings are a draft** ("Ada perubahan belum disimpan") saved with "Simpan Perubahan": card types/MDR Default, each bank's MDR override, and the QRIS image. Switching method with unsaved edits asks first.
- **Bank / e-wallet accounts are not a draft.** The panel lists the store's active accounts (Bank | Nomor rekening | Atas nama | Aksi) with a "Tambah Bank" / "Tambah E-Wallet" button. The button opens `ChannelAccountDialog` (provider dropdown, account/phone number, holder name; all required) and "Simpan" writes straight to the server (`saveChannelMutation`). The dropdown lists `BANK_PROVIDERS` / `EWALLET_PROVIDERS` minus the ones already added — **one account per provider name** (the card panel's MDR table is keyed by bank name). Edit reopens the dialog with the provider locked. "Hapus" asks first, then sets the channel `inactive` (channels are never deleted — payments reference them); adding the same provider again reactivates that row via PUT instead of creating a duplicate. The number may only contain digits, spaces, `-` and `+` (same rule as the backend, `accountNumberError`).
- **Per-bank MDR override:** each bank can have its own MDR (`mdr_percent` on the bank's payment channel, `null` = none, `0` = no MDR). The card panel shows the active banks (the same list as Transfer Bank) in a BANK / MDR / STATUS table ("Override" when set, else "Menggunakan default"); the method-level "MDR Default" is used for banks without an override. The override is saved with the bank (`PUT /master/payment-channels/:id`, omitted when blank), and any PUT of a channel must resend it (the transfer panel does).
- **MDR is recorded, not charged**: at checkout the backend computes `mdr_amount` = grand total × (the paid bank's `mdr_percent`, else the method's `mdr_percent`) for debit and credit alike and stores it on the payment (`mdr_percent`/`mdr_amount`). Payment `amount` = grand total — the customer is never charged extra. Older payments keep their `surcharge_amount`. `payment_channel_id` is optional: the cashier app only needs to send it (the store's bank) for the bank's MDR override to apply; without it the MDR Default is used.
- Legacy: stores may have several rows of one type from the old free-form screen; the oldest is the one managed here (and gets renamed to the canonical name on the next save).

Sublayers: `api/` (multipart service for methods + channels), `constants/` (method types, card options, provider suggestions, `TYPE_META` icon/tile colour), `components/` (`MethodListItem`, `MethodDetailPanel`, `ConfigPanels` — card / channel / QRIS, `ChannelAccountDialog` — add/edit a bank or e-wallet account, `OptionChip` — the pill used for card types, `method-draft` — card/QRIS draft model & dirty check), `schemas/` (`channel-account.schema.ts`), `section/` (`PaymentMethodSection.tsx` — queries, immediate toggles and account saves, draft save).
