# modules/public/store-registration

Public self-service store registration at `/daftar` — where the landing page's "Daftar Early Access" (and the Starter/Pro plan buttons) lead. Built from the Stitch "Pendaftaran Bisnis" design, adapted to what `pos-kasir-be` actually does.

**Backend:** `POST /internal/store-registrations` (`internal/central/store_registration`, public — no token, no `X-Store-Code`). It's mounted on the backend's outer router, **not under `/api/v1`**, so `infrastructure/` resolves it against the API origin rather than `apiClient`'s baseURL. Submitting only queues a `pending` registration; an internal admin (Neela Control) approves it — which runs tenant onboarding on the **Starter** plan (`store_registration.DefaultPlan`) — or rejects it. The success screen says exactly that ("sedang ditinjau"), not "toko siap".

**Fields** = `dto.SubmitRegistrationRequest`, with the same limits in `domain/store-registration.schema.ts`: `store_name` (3–150), `address` (≤255), `phone_no` (≤30), `owner_name` (3–150), `owner_username` (3–100), `owner_email` (email, ≤150), `owner_phone_no` (optional, ≤30), `password` (≥8). Password confirmation, the strength meter and the consent checkbox are client-side only. Errors: `409 CONFLICT` for an email that already has an active store or a pending registration — told apart by message and shown on the email field.

**Plan picker (left panel):** driven by `presentation/registration-plans.ts`. Only **Starter** is `available` today — the submit body has no plan field and the backend provisions every approved registration on Starter — so Pro is shown as "Segera hadir" (disabled). The landing's plan buttons link to `/daftar?paket=<id>`; a plan that isn't selectable (e.g. `?paket=pro`) falls back to Starter with a notice that the upgrade is done by the team after activation. Set `available: true` on a plan (and send it in the payload) once the backend accepts a plan on registration.

**Beli langsung (pay while registering):** the form has a "Cara Memulai" choice — **Coba Gratis** (the original flow: register, no payment) or **Beli Langsung Starter 1 Bulan** (`PurchaseModeField`). `?mode=beli` preselects the paid option; the landing's Starter card has a "Beli Starter 1 Bulan" button linking to `/daftar?paket=starter&mode=beli`. Paid flow: submit the registration as usual → on success `RegistrationPaymentDialog` opens → `POST /internal/store-registrations/payment` returns a Midtrans **Core API QRIS** charge (`qr_string`, `amount`, `expires_at`, 15-minute QR; **no Snap**, so no client key/snap.js) → the dialog draws the QR with `qrcode.react` and polls `POST /internal/store-registrations/payment/status` every 3 s until `PAID` (or `EXPIRED`/`FAILED`/`CANCELLED`, which offer "Buat QR baru"). Both endpoints are public and on the outer router like submit; there is no account yet, so the **email + password from the form** are the proof of ownership (same as the status check) and are kept only in `StoreRegistrationPage` state. The plan is always Starter and the **amount comes from the backend's `subscription_plan` table** (the `Rp99.000` on the page is display-only — keep `MONTHLY_PRICE.starter` in sync with that table). Reopening the dialog ("Bayar Sekarang" on the success screen) returns the still-valid QR or the paid payment rather than charging twice. Payment doesn't skip review: the success screen still says the registration is under review, and the paid month starts **when the admin approves** (the backend sets `stores.renew_at` then). The QR is requested with `useQuery` keyed by an attempt counter, not `useMutation` — a mutation's observer is detached by StrictMode's dev remount and never receives the response. Errors (`PAYMENT_PROVIDER_NOT_CONFIGURED` 503, `PAYMENT_PROVIDER_UNAVAILABLE` 502, `INVALID_CREDENTIALS` 401, `REGISTRATION_NOT_PAYABLE` 400) map to Indonesian messages in `application/useRegistrationPayment.ts`. The free trial has no backend support (no trial length is enforced); only the paid path is wired to a gateway.

**Differences from the Stitch design:** "Kategori Bisnis" and "Kota Operasional" → replaced by store address + phone (the backend stores no category/city); the customer review card, the "Paket Pro Gratis — Akses Penuh Tanpa Batasan" framing, "langsung aktif 10 menit", OTP wording, the SSL/"Standar QRIS BI"/"Kominfo" badges, the PT name and the 3-step header nav are dropped (not true for this flow yet); an "Alur Pendaftaran" card explains the approval step instead. A logged-in owner visiting `/daftar` is redirected to `/app`.

**Status screen (`/status-pendaftaran`, `RegistrationStatusPage`):** an owner has no account until an admin approves the request, so this public page is how they see whether it was approved. It calls `POST /internal/store-registrations/status` (public, same outer-router origin as submit) with the **email + password chosen at registration** — the password is the proof of ownership, so a stranger who knows the email can't read the status or rejection reason. Unknown email and wrong password are the same `401 INVALID_CREDENTIALS` (shown on the password field). Response (`CheckRegistrationStatusResponse`): `status` `pending | approved | rejected`, `store_name`, `rejection_reason?`, `created_at`, `processed_at?`; it reports the **latest** registration for that email (a rejected one can be resubmitted). Views: pending ("Perbarui Status" re-runs the lookup), approved ("Masuk ke Portal" — provisioning is async, so the copy tells them to retry after a few minutes), rejected (reason + "Daftar Ulang"). The password is held in component state only, never in the URL/storage; `RegistrationSuccess` links here passing the email via router state (not a query string). Also linked from the registration form footer and the login page. A logged-in owner is redirected to `/app`. Backend side: `pos-kasir-be` `internal/central/store_registration` (`CheckStatus`).

Layers (per `ARCHITECTURE.md`'s `modules/public` convention): `domain/` (types hand-transcribed from the internal swagger instance — not generated — plus the zod schema), `infrastructure/` (API call), `application/` (`useSubmitRegistration`, conflict mapping), `presentation/` (page + components). Shared public bits (`NeelaWordmark`, `waLink`, `useIsOwnerSession`, plan facts) live in `modules/public/shared/`.
